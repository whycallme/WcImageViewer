# v0.3 UI 크롬 시안 — WC Image Viewer

메인 창의 외관 개선 1단계 산출물. **`src/`는 건드리지 않았다.** 이 폴더의 HTML/PNG/Python만 추가했다.
목표는 "얇고 깔끔하고 세련된 이미지 뷰어" — 창과 버튼이 화면을 덜 차지하되, 버튼을 숨기지 않는다.
이 문서 끝의 **최종 결정**에서 실제 구현 방향(B — Seamless, 28px)을 확인한다. 본문의 추천은 구현 전 판단이다.

- `gallery.html` — 시안 3종을 나란히 놓고 비교하는 갤러리
- `*.png` — 1280×800 실제 렌더링 (일반/호버 각 1장) + 800×600 검증 1장
- `render_mockups.py` — HTML 생성 + Edge headless 렌더 + 실측 (`measurements.json`)
- `measurements.json` — 1280×800 / 800×600 실측 원본

## 1. 공통 전제

| 항목 | 값 |
|---|---|
| 캔버스 | 1280×800 (창 콘텐츠 전체, OS 프레임 제외) |
| 사진 | `C:\Windows\Web\Wallpaper\Windows\img0.jpg` (3840×2400) |
| 폰트 | Segoe UI / Malgun Gothic |
| 팔레트 | 배경 `#1E1E1E`, 툴바 `#252526`, 버튼 `#3A3A3D`, 테두리 `#4A4A4E`, 강조 `#E8A33D` |
| 렌더 | Edge headless, 100% DPI, `--force-device-scale-factor=1` |
| 썸네일 | 8장, 선택 4번째. 호버 시안은 6번째에 마우스가 있다고 가정 |

- PNG는 창 콘텐츠만 담는다. `WindowChrome`을 쓰면 타이틀바까지 앱이 그리므로 이 캔버스가 곧 창이다.
- 사진은 구도 확인용으로 `object-fit: cover` 크롭했다. 실제 표시 모드(맞춤/100%)에 대한 주장이 아니다.
- 썸네일 8장은 같은 사진의 크롭/색조 변형이다. 실제 폴더의 썸네일 밝기 편차를 흉내 낸 것.
- 세 시안 모두 11개 컨트롤과 최소화/최대화/닫기를 포함한다. B는 아이콘 단독이므로 매핑을 명시한다.

### B(Seamless) 아이콘 매핑

| 컨트롤 | 아이콘 | 컨트롤 | 아이콘 |
|---|---|---|---|
| 파일 열기 | 페이지 + 산 | 슬라이드 | ▶ |
| 폴더 열기 | 폴더 | 최근 | 시계 |
| 이전 / 다음 | ‹ / › | 설정 | 톱니(8-spoke) |
| 맞춤 | 네 모서리 확장 | 100% | `1:1` |
| 배율 입력 | `100%` 필드 | 창 맞춤 | 모니터 + 이미지 |

## 2. 측정값

`measurements.json`의 실제 레이아웃 결과. 높이는 CSS px(= WPF DIP), 100% DPI 기준.

| 시안 | 타이틀바 | 툴바 | 크롬 합계 | 이미지 영역 @1280×800 | 썸네일 스트립 | 썸네일 |
|---|---:|---:|---:|---:|---|---:|
| A Graphite | 32 | 34 | **66** | 638 | 96 (레이아웃) | 72×72 |
| B Seamless | — (통합) | 38 | **38** | 762 | 74 (이미지 위 오버레이) | 54×54 |
| C Editorial | 28 | 36 | **64** | 648 | 88 (레이아웃) | 52×52 |

현재 앱은 Windows 기본 타이틀바(≈32) + 약 40px 툴바 = 약 72px. A는 66, C는 64로 6–8px 줄고,
B는 38로 34px 줄어든다. A와 C의 차이는 2px뿐이므로 "얇음"만으로는 고를 이유가 약하다.

### 버튼 히트 영역 (가로 × 세로)

| 시안 | 툴바 버튼 | 배율 입력 | 창 버튼 | 썸네일 |
|---|---|---|---|---|
| A | 46–73 × 28 | 56 × 26 | 46 × 32 | 72 × 72 |
| B | 32 × 32 | 52 × 24 | 46 × 38 | 54 × 54 |
| C | 40–67 × 32 | 46 × 24 | 44 × 28 | 52 × 52 |

A의 라벨 폭은 "이전/최근/설정" 46px에서 "파일 열기/슬라이드" 70–73px까지. C는 텍스트만 있지만
좌우 8px 패딩을 넣어 최소 40×32를 확보했다. B는 32×32로 가장 작고, 창 버튼만 46×38이다.

### 800×600 최소 크기

각 시안의 툴바 콘텐츠 폭(11개 컨트롤 + 구분선)을 실제로 레이아웃한 값:

| 시안 | 콘텐츠 폭 | 가용 폭 @800 | 여유 | 결과 |
|---|---:|---:|---:|---|
| A | 707 | 784 | **+77** | 통과 (스크린샷 `a-graphite-800x600.png`) |
| B | 706 | 790 | **+84** | 통과 |
| C | 627 | 760 | **+133** | 통과 |

A는 800×600에서 이미지 영역 438px, 썸네일 96px, 툴바 11개 + 창 버튼 전부 표시. 잘림/줄바꿈 없음.
(측정은 `measurements.json`의 `a-normal-800x600` 참조. Edge의 dump-dom은 창 프레임 24×92를 포함하므로
같은 콘텐츠 박스가 나오도록 보정했고, 스크립트가 viewport를 assert한다.)

## 3. 비교표

| 시안 | 타이틀바+툴바 | 히트 영역 | 발견성 | 구현 난이도 (WindowChrome) | 대화상자 톤 일관성 | 장점 | 단점 |
|---|---:|---|---|---|---|---|---|
| **A Graphite** | **66 px** (32+34) | 46–73×28 | **높음** — 9개 텍스트 + 2개 아이콘 + 입력 | **낮음–중간** — 캡션 32px, 툴바 구조 거의 유지 | **높음** — 기존 채워진 버튼/3px 라운드/12px 그대로 | 라벨이 전부 보이고, 800×600에서 77px 여유, 대화상자를 안 건드림 | B보다 28px 두껍고, 버튼 폭이 제각각 |
| **B Seamless** | **38 px** (한 줄) | 32×32 | 중간 — 아이콘 + 툴팁 | **중간–높음** — 캡션 안 10개 hit-test, 도크 블러 | 낮음 — 아이콘 바/도크에 대응하는 대화상자 없음 | 이미지 762px, 가장 얇고 몰입감 있음 | 발견성이 툴팁에 의존, 도크 blur는 WPF에서 비쌈 |
| **C Editorial** | **64 px** (28+36) | 40–67×32 | 중간–높음 — 라벨, 저대비 | 낮음–중간 — 캡션 28px이 얇을 뿐 구조는 단순 | 중간 — 대화상자도 얇게 재스킨해야 함 | 여백/타이포로 64px가 더 가볍게 읽힘, 133px 여유 | 28px 드래그 영역, 저대비, 대화상자 재작업 |

### A — Graphite

- **무엇**: 32px 커스텀 타이틀바(파일명 + 창 버튼) + 34px 툴바. 모든 라벨 유지, 앰버는 선택/포커스에만.
- **장점**: 발견성 최상. Settings/Bookmark/Rename의 기존 버튼 스타일과 톤이 같아 재스킨 범위가 0.
  800×600에서 77px 여유. 툴바가 기존 `DockPanel + StackPanel` 구조와 거의 1:1이라 구현이 가장 예측 가능.
- **단점**: "얇다"는 목표에는 B보다 못 미친다. 라벨 폭이 들쭉날쭉해 정렬이 느슨해 보일 수 있음.
- **호버**: `맞춤` 버튼이 밝아지고 앰버 밑줄 + 툴팁, 선택 썸네일은 앰버 2px, 호버 썸네일은 흰 1px 링.

### B — Seamless

- **무엇**: 타이틀바와 툴바를 38px 한 줄로. 왼쪽 앱 마크/이름, 아이콘 10개 + 배율 입력, 오른쪽 창 버튼.
  썸네일은 이미지 위에 뜬 반투명 도크(74px)로 이동.
- **장점**: 크롬 38px, 이미지 762px. 사진이 가장 크고, 도크가 이미지 가장자리를 끊지 않는다.
- **단점**: 아이콘 단독은 툴팁을 배우기 전까지 발견성이 가장 낮다. 캡션 영역에 인터랙티브 컨트롤이
  많아 `IsHitTestVisibleInChrome` 누락 시 창 드래그로 먹힌다. CSS `backdrop-filter`는 WPF에 없어
  반투명 단색/스냅샷 블러로 대체해야 한다. 대화상자와 톤이 가장 멀다.
- **호버**: `맞춤` 아이콘 배경 + 툴팁("창에 맞춤 0"), 6번째 썸네일 흰 링.

### C — Editorial

- **무엇**: 28px 초박형 타이틀바(가운데 대문자 워드마크) + 36px 텍스트 툴바. 선 대신 20–34px 여백,
  호버만 앰버 1px 밑줄. 정보 오버레이는 앰버 세로선 + letterspaced 대문자 파일명.
- **장점**: 64px인데 A보다 가볍게 읽힌다. 모든 라벨이 보이고 800×600에서 133px 여유.
  강조를 밑줄 하나로 통일해 상태 표현이 일관적.
- **단점**: 28px 타이틀바는 Windows 기본 32px보다 낮아 드래그 영역이 얇고, 창 버튼 44×28은
  터치 44px 세로 가이드에 못 미친다. 저대비 텍스트는 밝은 사진에서 약해 보일 수 있다.
  대화상자의 채워진 버튼과 맞추려면 Settings/Bookmark/Rename도 얇게 손봐야 한다.
- **호버**: `맞춤` 텍스트가 흰색 + 앰버 밑줄, 배율 입력 포커스, 6번째 썸네일 밝아짐.

## 4. WPF 구현 가능성 (제약 명시)

권장 구현은 `WindowChrome` 기반이다. `AllowsTransparency=True`는 쓰지 않는다 — 네이티브 리사이즈/Aero Snap/
최대화 애니메이션이 깨진다.

| 제약 | 설계·대응 |
|---|---|
| **WindowChrome** | `WindowStyle=None`, `ResizeMode=CanResize`, `WindowChrome.CaptionHeight` = A 32 / B 38 / C 28 (DIP). 캡션 안 버튼은 `WindowChrome.IsHitTestVisibleInChrome="True"`. 툴바는 캡션 밖. |
| **네이티브 리사이즈/스냅/최대화** | WindowChrome이 DWM 리사이즈 테두리를 유지한다. 최대화 시 1px 오버플로는 `WM_GETMINMAXINFO`(또는 `MaxHeight` 보정)로 처리. 더블클릭 최대화, Win+화살표, 스냅 레이아웃은 그대로. |
| **F11 전체화면** | 기존 `ToggleFullscreen()`이 `WindowStyle`/`ResizeMode`/`WindowState`/bounds를 저장·복원한다. 커스텀 크롬에서는 추가로 크롬 행을 `Collapse`하고 `CaptionHeight=0`으로 내린 뒤 복원. 기존 코드와 충돌 없음. |
| **High-DPI** | 모든 값은 DIP. 32px → 40px @125%, 48px @150%. 아이콘은 `Path`/`Viewbox` 벡터, 폰트는 12/13px DIP. 스크린샷은 100%지만 DIP 수치는 그대로 유효. |
| **최소 창 800×600** | A 707/784(+77), B 706/790(+84), C 627/760(+133). `MinWidth=800`, `MinHeight=600` 유지. A는 실제 800×600 스크린샷으로 확인. |
| **대화상자 톤** | Settings/Bookmark/Rename은 현재 채워진 `#3A3A3D` 버튼 + 3px 라운드. A는 그대로 맞고, C는 대화상자까지 재스킨해야 하며, B는 대응물이 없다. |
| **발견성** | A/C는 라벨, B는 툴팁. B를 채택한다면 최초 실행 시 1회 툴팁 힌트나 키보드 포커스 링이 필요. |

### 구현 메모

- A의 툴바는 기존 `MainWindow.xaml`의 `ToolbarBorder` 안 `StackPanel`을 거의 그대로 쓰고
  타이틀바만 추가하면 된다. `Padding="8,6"` → `0 8px`, 버튼 높이 28로 조정.
- B는 `CaptionHeight=38` 안에 10개 버튼이 들어가므로 각 버튼에 `IsHitTestVisibleInChrome`을 빠짐없이 준다.
  도크는 `Grid` 오버레이 + 반투명 `#CC101013` 브러시로 시작하고, 블러는 성능 확인 후 옵션.
- C는 타이틀바 28px에서 창 버튼 44×28을 유지한다. 드래그 영역이 28px뿐이므로 상단 8px는
  반드시 캡션이 되도록 `CaptionHeight=28`을 정확히 준다.
- 세 시안 모두 창 버튼은 오른쪽 46px(A/B)/44px(C) 폭. Windows 11의 46px 관례와 맞춘다.

## 5. 검증한 것 / 못 한 것

- PNG 7장을 System.Drawing으로 열어 크기/픽셀 포맷을 확인했고, 6장은 1280×800, 1장은 800×600이다.
  (용량 398–761KB, 빈 이미지 아님.)
- `gallery.html`은 7장 전부를 `<img>`로 참조한다.
- 800×600은 A만 스크린샷이 있고, B/C는 실측 콘텐츠 폭으로 통과를 확인했다.
- 정적 시안이므로 실제 키보드 포커스 링, 툴팁 지연, 창 드래그 커서는 그리지 않았다.
- WPF에서의 실제 리사이즈/스냅/최대화/F11은 아직 구현 전이다. 이 문서는 설계 제약 검토이지 구현 검증이 아니다.
- B의 `backdrop-filter`와 C의 28px 캡션은 실제 WPF에서 재확인이 필요하다.

## 구현 전 초기 추천: A — Graphite

> 아래 추천은 시안 비교 단계의 초기 판단이다. 실제 선택과 구현 결과는 맨 끝의 **최종 결정: B — Seamless**를 따른다.

1. **66px 크롬에 라벨 11개를 모두 남기고도 800×600에서 77px가 남는다** — 발견성과 최소 크기를 동시에 만족하는 안.
2. **기존 팔레트·버튼·3px 라운드·대화상자 톤을 그대로 쓴다** — `src/`의 Settings/Bookmark/Rename을 재스킨하지 않아 회귀 범위가 가장 작다.
3. **WindowChrome 캡션 32px + 기존 툴바 구조 유지로 리사이즈/스냅/최대화/F11 리스크가 가장 낮다** — B의 캡션 hit-test와 도크 블러, C의 28px 드래그 영역 같은 새 위험이 없다.

## 최종 결정: B — Seamless

- 사용자가 A/B/C 시안을 비교한 뒤 **B — Seamless**를 선택했다.
- 실제 구현에서는 크롬을 시안의 38px에서 **28px**로 한 번 더 줄였고, 썸네일을 하단 전체 폭 스트립 대신 **74px 플로팅 도크**로 옮겨 화면 점유를 줄였다.
- 아이콘 단독 버튼의 발견성은 한국어 툴팁, 단축키 표기, `AutomationProperties.Name`으로 보완했다.
- 이 폴더의 측정값(38px 크롬, 이미지 영역 762px 등)은 **시안 기준**이며 최종 구현 크롬은 28px다. 800×600 실측과 버튼 히트 영역도 시안 값이다.
- QA 스크린샷(`impl*.png`, `theme-*.png`)은 저장소에 커밋하지 않고 로컬 검증용으로만 보관한다(`.gitignore`).
- `assets/img0.jpg`는 Windows 기본 배경화면을 빌려 쓴 목업 맥락용 사진이며, 앱 배포물(ZIP)에는 포함되지 않는다.
